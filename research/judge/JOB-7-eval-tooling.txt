DEEPEVAL (G-Eval, pytest-style)
Repo: https://github.com/confident-ai/deepeval
Last commit: 2026-10-03. Licence: Apache-2.0 (LICENSE.md, "Apache License Version 2.0"). Stars: ~19k.
Install: pip install -U deepeval. Python only.
What it is: a pytest-like runner. A metric returns a score and a pass/fail against a threshold, so it can fail a test run.
Paid API: README default is OpenAI. Quote: "Set your `OPENAI_API_KEY` as an environment variable (you can also evaluate using your own custom model...)". Local works: docs/content/integrations/models/ollama.mdx says "DeepEval allows you to use any model served by Ollama to run evals" and gives "deepeval set-ollama --model=deepseek-r1:1.5b". A 1.5B judge will be a weak judge; that is a quality issue, not a wiring issue.
Funnel warning: README pushes "Sign up for Confident AI" (their SaaS). The library works without it.
Custom criterion, verbatim from README.md:
    correctness_metric = GEval(
        name="Correctness",
        criteria="Determine if the 'actual output' is correct based on the 'expected output'.",
        evaluation_params=[SingleTurnParams.ACTUAL_OUTPUT, SingleTurnParams.EXPECTED_OUTPUT],
        threshold=0.5
    )
    assert_test(test_case, [correctness_metric])
How the judgement is structured: deepeval/metrics/g_eval/templates/generate_evaluation_steps.txt turns your criteria into steps ("generate 3-4 concise evaluation steps based on the criteria"), then generate_evaluation_results.txt asks for JSON: "`\"score\"`: an integer between {{ score_range[0] }} and {{ score_range[1] }}" plus a "reason". Score is normalised and compared with threshold.
SOURCE: confident-ai/deepeval README.md; docs/content/integrations/models/ollama.mdx; deepeval/metrics/g_eval/templates/generate_evaluation_results.txt and generate_evaluation_steps.txt; LICENSE.md
COSTS: pip install; OpenAI key by default OR local Ollama model (free, CPU/GPU you already have).

RAGAS
Repo: https://github.com/explodinggradients/ragas (README now points to vibrantlabsai/ragas; same history, ls-remote HEAD identical).
Last commit: 2026-02-24 ("fix: allow fork contributors in check-docs CI workflow (#2606)") - about 7 months before today. Treat as stale by the 6-month rule. Licence: Apache-2.0 (LICENSE). Stars: ~16k.
Install: pip install ragas.
Focus: RAG metrics first; custom criteria come through DiscreteMetric (README calls it Aspect Critique).
Paid API: README example builds "client = AsyncOpenAI()" and "llm_factory(\"gpt-4o\", client=client)". docs/howtos/customizations/customize_models.md says providers go through Instructor and LiteLLM ("100+ other providers"). A local/Ollama example: NOT FOUND in the fetched doc (grep for ollama returned nothing).
Custom criterion, verbatim from README.md:
    metric = DiscreteMetric(
        name="summary_accuracy",
        allowed_values=["accurate", "inaccurate"],
        prompt="""Evaluate if the summary is accurate and captures key information.

    Response: {response}

    Answer with only 'accurate' or 'inaccurate'."""
    )
    score = await metric.ascore(llm=llm, response="The summary of the text is...")
    print(f"Score: {score.value}")
Judgement structure: one prompt, closed set of allowed_values, returns .value and .reason. No pass threshold built into the metric; you write the assertion yourself.
Blunt take: slowing down (last commit Feb), API churn (old docs mention AspectCritic, new README uses DiscreteMetric), and the examples assume OpenAI.
SOURCE: explodinggradients/ragas README.md; docs/concepts/metrics/available_metrics/aspect_critic.md; docs/howtos/customizations/customize_models.md; LICENSE
COSTS: pip install; OpenAI-style client by default; local only via LiteLLM/Instructor wiring you do yourself.

    assert:
      - type: llm-rubric

LM-EVALUATION-HARNESS (EleutherAI)

Custom criterion means a YAML task with a programmatic metric. Verbatim from lm_eval/tasks/gsm8k/gsm8k.yaml:

    dataset_path: openai/gsm8k
    output_type: generate_until
    doc_to_text: "Question: {{question}}\nAnswer:"
    doc_to_target: "{{answer}}"
    metric_list:
      - metric: exact_match

VERDICT (my read of the 16 sections above, not an extra tool)
Can fail and run on one machine with local models, custom text criteria: inspect_ai (model_graded_qa template + code scorers), promptfoo (llm-rubric + deterministic asserts, YAML), deepeval (GEval, pytest threshold, Ollama documented), mlflow make_judge (Ollama documented). Lightweight scorers to embed: autoevals, openevals, the Anthropic cookbook 30-line grader. Benchmark-only, no custom taste criteria: lm-evaluation-harness, lighteval. Dormant: openai/evals (last real change before 2026-04). Slowing: ragas (2026-02-24). Source-available, not OSI: Phoenix (ELv2). Observability products with SaaS funnels: Langfuse, TruLens (Snowflake), Phoenix (Arize AX), Braintrust.
Caveat on all LLM-judge tools: a tiny local judge model will be an unreliable judge; the tooling only makes the failure visible, it does not make the judge correct. None of the fetched READMEs ships a judge-vs-human agreement test by default; mlflow (alignment.mdx) and trulens (docs "LLM judge alignment guide" link) point at it.
